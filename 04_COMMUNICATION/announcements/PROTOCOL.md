# 공지 확인·자동 수집 방법

## 기본 흐름

**본인이 로컬에 기록 → 관리 앱이 검증·수집 → 중앙에 동기화**합니다. 담당자마다 GitHub 커밋·수동 업로드를 할 의무는 없습니다. 관리 앱이 켜진 동안 연결된 프로젝트 경로를 반복 확인하고 중앙 공지를 로컬로 배포합니다. 기본 반복 간격은 로컬 배포·수집 약 15초, 중앙 GitHub 동기화 약 60초입니다. 앱 종료 중에는 수집하지 않습니다. 기존 Windows 로그인 시 앱 자동 시작 등록과 별개로, 로그인 전·앱 종료 상태의 상시 서비스라고 표현하지 않습니다.

1. 실제 프로젝트의 `_통합소통/받은공지/manifest.json`과 본인 `_통합소통/확인기록`을 비교합니다. 새·변경·미적용 공지를 본문으로 읽습니다. 마지막 중앙 동기화 상태가 오래됐거나 실패했으면 받은 내용을 최신이라고 단정하지 않습니다.
2. 실제 읽은 공지 ID·버전·해시와 본인 프로젝트·AI·세션·시간·적용 상태를 JSON으로 남깁니다. 자동 배포가 읽음이나 적용을 뜻하지 않습니다.
3. 기록은 `_통합소통/확인기록`에 둡니다. 앱은 현재 공지와 소유 경로·기록 형식을 검증해 중앙 `receipts/`로 수집합니다. 공유할 짧은 안내·진행·인수인계는 `보낼자료`에 둡니다.
4. 로컬 작성·앱 수집·중앙 공유를 따로 확인합니다. 인증·네트워크·실제 경로 미연결·파일 검증 문제는 대기로 인수인계합니다. 정상 동기화 전에는 다른 담당자에게 공유됐다고 보고하지 않습니다.

로컬 소통 폴더에 접근할 수 없는 작업 환경은 실제 프로젝트 위치 연결이 필요하다는 사실을 남깁니다. 현재 접근 가능한 중앙 공지를 읽는 것은 가능하지만, 독립 채팅이나 없는 프로젝트 폴더에 전달·확인됐다고 추정하지 않습니다.

## 프로젝트의 간편 기록 도우미

앱은 소통 폴더에 `_통합소통/README.md`와 `기록도우미.py`도 제공합니다. Python이 있으면 `_통합소통`에서 다음처럼 사용합니다. 추가 패키지는 필요 없습니다.

```text
python 기록도우미.py check --actor Sol --read
python 기록도우미.py ack --actor Sol --session 20261005-work --notice N-0001 --status applied --note "본인 작업에 실제 적용한 내용" --evidence README.md
```

`check --read`로 현재 새·변경·미적용 본문을 읽고 본인 읽기 기록을 남깁니다. `ack`는 이 읽기 기록과 현재 공지를 비교해 버전·해시를 확인합니다. 확인 없이 적용 완료를 자동 작성하지 않습니다. 읽었지만 반영이 남았으면 `--status pending`으로 이유를 적고, 반영 후 실제 근거와 함께 갱신합니다.

대상 프로젝트는 받은 목록의 `deliveredProjectId`로 지정됩니다. 담당자가 다른 프로젝트를 대신 선택할 필요가 없습니다. 기록은 로컬 `확인기록`에 생성되고 앱이 수집합니다. 도우미 실행 성공 자체가 중앙 공유 완료는 아닙니다. Python을 쓰기 어려운 환경은 아래 JSON 명세로 본인 파일을 직접 작성할 수 있으며 추가 설치나 GitHub 수동 업로드를 강제하지 않습니다.

## 세 폴더의 용도

| 위치 | 작성자 | 내용 |
|---|---|---|
| `_통합소통/받은공지` | 관리 앱 | 대상 공지 `N-xxxx.md`와 현재 `manifest.json` |
| `_통합소통/보낼자료` | 해당 작업 담당자 | 공유할 요약·질문·진행·인수인계 텍스트 |
| `_통합소통/확인기록` | 실제 읽은 본인 AI | 공지별 본인 확인 JSON |

받은 공지 본문을 로컬에서 임의 수정해 중앙 공지처럼 취급하지 않습니다. 변경 제안은 보낼자료로 남기거나 권한 있는 중앙 문서 작업에서 처리합니다. 실제 프로젝트의 원본·실행기·환경·데이터를 수집용으로 이동하지 않습니다.

## 본인 확인 JSON

`actorId`는 실제 AI 이름이나 역할 식별자입니다. 고정 ID는 Sol=`Sol`, Astra=`Astra`, B계정 Nova=`account-b-nova`입니다. 새 AI는 일관된 본인 ID를 사용합니다. `projectId`는 받은 목록의 `deliveredProjectId`이며 PC 메뉴의 내부 ID와 다를 수 있습니다. `sessionId`는 이번 작업 이름입니다.

파일명은 `json.dumps([actorId, sessionId], ensure_ascii=False)`의 UTF-8 SHA-256에 `.json`을 붙입니다. 기본 JSON 구분자 `, `를 유지합니다. `_통합소통/확인기록/<공지 ID>/r<버전>/` 아래에 둡니다. 같은 AI·세션이 다른 공지를 기록해도 서로 덮어쓰지 않게 하고, 다른 작성자의 파일은 수정하지 않습니다. 중앙 수집 위치는 `receipts/<공지 ID>/r<버전>/<projectId>/<해시 파일명>.json`입니다.

필수 필드: `schemaVersion: 1`, `noticeId`, `revision`, `contentSha256`, `projectId`, `actorId`, `sessionId`, `checkedAt`(시간대 포함 ISO 시각), `applicationStatus`, 구체적인 `note`, `evidence`(근거 경로 목록). 적용 완료에는 `appliedAt`도 기록합니다. 현재 받은 공지의 버전·해시를 실제 읽은 값으로 적고, 본인이 한 작업 범위만 설명합니다.

| 저장 값 | 사람용 표시 | 기록 조건 |
|---|---|---|
| `pending` | 읽음·적용 대기 | 읽었지만 반영이 남음 |
| `applied` | 적용 완료 | 본인 작업에 실제 반영하고 근거가 있음 |
| `not_applicable` | 해당 없음 | 현재 역할에 적용되지 않는 구체적인 이유가 있음 |
| `blocked` | 막힘 | 권한·환경·사용자 지시 등의 이유로 반영하지 못함 |

읽고 이해한 사실은 본인이 기록합니다. 같은 프로젝트의 다른 AI나 다른 프로젝트 담당자를 대신 체크하지 않습니다. 상태 변경 시 실제 확인 시각을 보존하고 적용 시각을 따로 기록합니다. 공지 버전·해시가 바뀌면 새 내용을 읽고 새 버전의 확인 기록을 남깁니다. 이전 기록은 삭제하지 않습니다.

## 자료와 기록 수집의 범위

현재 보낼자료 수집 대상은 하위 폴더를 포함한 **UTF-8 텍스트 `.txt`, `.md`, `.json`, 파일당 1MiB 이하**입니다. 중앙 `project-inbox/<projectId>/<내용 해시>/`에 원문 텍스트와 수집 정보를 연결하며 같은 내용을 반복 수집하지 않습니다. 파일 복사나 수집은 질문 해결·공지 적용 완료를 뜻하지 않습니다.

확인 JSON 형식 오류, 변경 중인 파일, 비밀값 패턴, 크기 초과·지원하지 않는 형식은 수집·공유 완료로 표시하지 않습니다. 연결·바로가기 경로를 따라 다른 원본까지 읽지 않습니다. 영상·오디오·모델·소설 원문·키·계정 내용은 소통 수집 대상에 넣지 않습니다. 원본은 자동 삭제하지 않습니다. 중앙에서 별도로 바뀐 본인 기록과 새 로컬 기록이 충돌하면 자동 덮어쓰지 않고 보류합니다. 파일 작성 중인 상태는 다음 수집 때 다시 확인하고, 형식·내용 문제는 담당자가 수정한 뒤 처리합니다.

각 프로젝트 Git에는 개인 소통 파일이 자동 포함되지 않게 `_통합소통/보낼자료/`, `_통합소통/확인기록/`, `_통합소통/.communication-imports.json`의 제외 여부를 해당 담당자가 확인합니다. 기존 추적 파일을 이 안내만으로 삭제하거나 저장소를 초기화하지 않습니다.

## 중앙과 로컬의 차이

허브 기본 공지 대상은 등록 9개, 기존 Burgundy·SideMemojang 방, 통합 관리, 영상 저장, 멀티의 신 서버의 **14개**입니다. FinanceOne·ASCII Aquarium은 경험 자료로 별도 집계하며 실제 비활성이라고 추정하지 않습니다. 그 작업을 재개하는 AI도 공지를 읽습니다.

기존 PC의 **6개 메뉴 진입점**은 이 14개 대상 전체와 같지 않습니다. 서버 운영 기능이 추가돼도 기본 공지 대상 전체의 연결을 뜻하지 않습니다. 실제 연결 근거가 확인된 ID 대응은 다음과 같습니다.

| PC 메뉴 ID | 중앙 공지 ID |
|---|---|
| `phonelol-current` | `PhoneLOL` |
| 게임의 실제 서버 운영 루트 | `PhoneLOL-Server` |
| `audiobook` | `Mushoku-Audiobook` |
| `video-downloader` | `Video-Downloader` |
| `project-operations-hub` | `Control-Tower` |

서버 운영 루트는 `C:\Users\user\Documents\MultiGod\PhoneLOL_LocalRuntime`으로 게임 개발 루트와 다릅니다. 서로 별도의 소통 폴더를 연결하고 확인 기록을 대신 승계하지 않습니다. [N-0006](notices/N-0006.md)과 [서버 근거](../../ai-control-tower/docs/MULTIPLAYER_SERVER.md)를 확인합니다.

`stock-planned`, `housing-planned`는 확인 당시 빈 준비 폴더입니다. 소통 대상 별칭을 지정하더라도 기존 Investment-Lab·ChungYack 개발 저장소가 연결됐거나 동작한다고 확대하지 않습니다. 나머지 대상의 실제 폴더는 확인·추가 연결이 필요합니다. 폴더명만으로 ID를 추정하거나 없는 경로를 대신 만들지 않습니다.

앱의 로컬 배포·수집과 중앙 동기화는 독립 상태입니다. 중앙을 읽거나 쓸 계정 인증·저장소 권한이 없거나 오프라인이면 마지막 정상 공지와 미공유 자료를 보존하고 대기로 둡니다. `STATUS.md`는 마지막 중앙 집계이며 모든 독립 채팅의 실시간 감시 결과가 아닙니다. 주기 수집을 확인했다고 PC 로그인 전·앱 종료 후에도 계속 동작하는 서비스라고 주장하지 않습니다.

## 중앙 공지 관리와 보조 CLI

중앙 작업자는 `notices/N-xxxx.md`와 `manifest.json`을 같은 변경에서 갱신합니다. 본문 의미가 바뀌면 버전을 올리고, UTF-8 BOM을 제외하고 CRLF/CR을 LF로 통일한 SHA-256을 기록합니다. 옛 해시의 확인은 현재 확인이 아닙니다. 종료 공지는 `active: false`로 보존합니다.

기존 `scripts/notice_board.py`는 중앙 저장소의 본문 조회·본인 확인·형식 검사·현황 생성을 하는 보조 도구입니다. 프로젝트 로컬에서는 위의 `기록도우미.py`를 사용합니다. 중앙 CLI와 관리 앱의 수집을 구분하며 중앙 도구 사용이나 GitHub 직접 업로드를 모든 담당자에게 강제하지 않습니다.

```text
python scripts/notice_board.py check --project Control-Tower --actor <본인 AI ID> --read
python scripts/notice_board.py validate
python scripts/notice_board.py status --write
```

중앙에 직접 기록을 반영하는 환경에서도 본인 기록만 병합하고 다른 기록을 강제 덮어쓰지 않습니다. 정책·사람용 안내·프로젝트 인수인계도 변경 내용과 함께 맞춥니다. [N-0001 버전 2](notices/N-0001.md)와 [N-0005](notices/N-0005.md)가 현재 자동 소통 절차입니다.

프로젝트 루트의 `AGENTS.md`에는 통합 소통 진입 안내만 표시된 관리 구역으로 연결합니다. 기존 규칙은 보존하고 구역이 불완전하거나 변경 중이면 보류합니다. 작업을 재개하는 AI가 실제 새 공지를 읽고 본인 기록을 남겨야 합니다.
