# Tool Candidates — 사람용 설명판

마지막 정리: **2026-09-13**

이 문서는 기술 용어를 아는 사람만 보라고 만든 목록이 아닙니다.
**“그래서 이게 뭐고, 나한테 뭐가 좋은데?”**를 먼저 설명하고, 설치·주의사항은 그 뒤에 적습니다.

상태 뜻도 간단합니다.

- `먼저 시험` = 좋아 보이니 작은 테스트부터 해볼 가치 큼
- `프로젝트용` = 특정 프로젝트에서 필요할 때 쓰면 좋음
- `후보` = 알아둘 가치는 있지만 당장 설치할 필요 없음
- `보류` = 지금 우리 환경에서는 번거롭거나 위험/비용이 더 큼

# 1. AI 작업 방식 / 플러그인 / 협업

## OpenAI Plugins
링크: https://github.com/openai/plugins

**한 줄 설명:** Codex에 기능 묶음을 붙일 때 참고하는 공식 플러그인 예제 모음입니다.

**쉽게 말하면:**
Codex에 “Figma 작업용 세트”, “Notion 작업용 세트”, “웹앱 제작용 세트”처럼 **기능 꾸러미를 추가하는 방식**을 보여주는 공식 예제집입니다.

**우리한테 왜 쓸모 있나:**
나중에 Project Operations Hub의 Skill, MCP, 명령을 하나의 Codex 플러그인으로 묶을 때 기준으로 삼기 좋습니다.

**설치/비용:** 필요한 플러그인만 Codex 쪽에서 설치합니다. 플러그인이 연결하는 외부 서비스에 따라 로그인이나 비용이 생길 수 있습니다.

**판단:** `후보`

## AGENTS.md
링크: https://agents.md/

**한 줄 설명:** AI에게 “이 프로젝트에서는 이렇게 일해라”라고 알려주는 공용 규칙 파일 방식입니다.

**쉽게 말하면:**
README가 사람용 설명서라면 AGENTS.md는 **AI용 작업 설명서**입니다.
예를 들어 “빌드는 이 명령”, “이 폴더는 건드리지 마”, “테스트는 여기까지 해야 완료” 같은 내용을 적습니다.

**우리한테 왜 쓸모 있나:**
이미 우리 Hub가 이 방식을 쓰고 있습니다. 다만 오래된 규칙을 계속 쌓지 않고 현재 필요한 내용만 남기는 식으로 운영합니다.

**설치/비용:** 설치 없음. 파일만 작성하면 됩니다.

**판단:** `형식은 이미 참고 중`

## Ponytail
링크: https://github.com/DietrichGebert/ponytail

**한 줄 설명:** AI가 간단한 일을 괜히 거대한 구조로 만들지 못하게 제동을 거는 플러그인입니다.

**쉽게 말하면:**
AI에게 일을 시켰는데 원래 파일 두 개 고치면 될 일을 새 프레임워크 만들고, 패키지 잔뜩 설치하고, 구조까지 갈아엎는 경우가 있습니다.
Ponytail은 **“있는 걸 먼저 써라 → 표준 기능을 써라 → 그래도 안 되면 최소한만 추가해라”** 쪽으로 AI를 몰아갑니다.

원래 이 링크를 볼 때 핵심도 “AI가 너무 오버엔지니어링하지 않게 한다”는 쪽으로 보면 됩니다.

**우리한테 어디에 좋나:**
- 작은 UI 수정
- 기존 앱에 기능 하나 추가
- 쓸데없는 새 의존성 방지
- 기존 Known-Good를 최대한 유지해야 하는 작업

**주의:** 너무 강하게 쓰면 필요한 기능까지 줄여버릴 수 있습니다. 그래서 우리 규칙인 **“구현은 단순하게, 요구사항은 절대 줄이지 않기”**와 함께 써야 합니다.

**설치:** Codex Plugin 형태로 시험 가능. Claude/Copilot/Gemini/OpenCode 계열도 지원합니다.

**판단:** `먼저 시험`

## FrontierAgent
링크: https://github.com/ApodexAI/FrontierAgent

**한 줄 설명:** 한 AI가 혼자 일하거나 여러 AI를 팀처럼 나눠 병렬 작업하게 하는 별도 Agent 프로그램입니다.

**쉽게 말하면:**
큰 일을 하나 시키면 내부에서 **팀장 AI + 여러 작업자 AI**처럼 나눠서 조사, 파일 작업, 검토를 동시에 시도할 수 있는 별도 실행환경입니다.

예:
`큰 프로젝트 조사 → A는 코드 구조 / B는 버그 / C는 문서 / 팀장이 합치기`

**우리한테 어디에 좋나:**
엄청 큰 저장소 분석이나 파일이 많은 조사에서 비교 실험할 수 있습니다.

**왜 바로 안 쓰나:**
지금도 ChatGPT Work/Codex가 비슷한 일을 어느 정도 하므로 기능 중복이 큽니다. 또 파일/명령 실행 권한이 큰 Agent라 안전범위를 먼저 확인해야 합니다.

**Windows:** 네이티브 Windows보다는 macOS/Linux 쪽 설명이 강해서 우리 PC에서는 WSL 포함 시험이 필요합니다.

**판단:** `후보`

## Gentle-AI
링크: https://github.com/Gentleman-Programming/gentle-ai

**한 줄 설명:** Codex·Claude·Cursor 같은 AI 개발도구에 공통 작업 습관을 한꺼번에 세팅해주는 구성 도구입니다.

**쉽게 말하면:**
각 AI마다 기억 방식, 설계 방식, 검토 규칙, Skill, MCP 설정이 따로 놀지 않게 **“우리 팀 개발 방식”을 한 번에 입히는 도구**에 가깝습니다.

**우리한테 어디에 좋나:**
Project Operations Hub에서 만든 규칙을 여러 AI 환경에 적용하는 아이디어를 비교해볼 수 있습니다.

**왜 조심하나:**
우리 Hub도 이미 규칙과 작업방식을 관리하므로 Gentle-AI까지 전역으로 넣으면 **같은 일을 두 군데서 지시해서 충돌**할 수 있습니다.

**판단:** `후보`

**한 줄 설명:** AI나 프로그램이 컴퓨터에서 아무 데나 접근하지 못하게 울타리를 치는 보안 도구입니다.

**쉽게 말하면:**

**우리한테 어디에 좋나:**
새 GitHub Agent나 MCP를 시험할 때 혹시 모를 파일 접근을 제한하는 용도입니다.

**왜 보류인가:**
현재 핵심 지원이 macOS/Linux 중심이라 Windows 네이티브가 주환경인 우리에게는 바로 쓰기 애매합니다. WSL 실험용으로는 가치가 있습니다.

**판단:** `보류`

링크: https://github.com/jo-inc/camofox-browser

**한 줄 설명:** AI가 웹사이트를 자동으로 돌아다니게 해주는 특수 브라우저 서버입니다.

**쉽게 말하면:**
일반 자동화 브라우저보다 실제 브라우저처럼 보이게 하면서, AI가 페이지 요소를 안정적으로 찾고 클릭·읽기 쉽게 만든 도구입니다.

**주의:** 사이트의 자동화 차단을 우회하는 쪽 기능도 강하므로 서비스 약관을 어기는 용도로 쓰면 안 됩니다. 로그인 쿠키와 세션 관리도 주의해야 합니다.

## Tencent TeamAI
링크: https://github.com/Tencent/teamai-cli

**한 줄 설명:** 여러 사람이 서로 다른 AI를 써도 **팀 규칙과 지식을 자동으로 똑같이 맞춰주는 도구**입니다.

**원래 게시물식으로 쉽게 말하면:**
회사에서 누구는 Claude Code, 누구는 Codex, 누구는 Cursor를 쓰면 각자 AI 설정이 따로 놀 수 있습니다.
TeamAI는 한 명이
`Skill / 규칙 / MCP / 팀 지식`
을 고치면 다른 팀원의 AI에도 동기화하고, 실수와 수정 경험도 팀 지식으로 쌓는 쪽입니다.

**우리한테 왜 특히 중요하나:**
우리가 만든 Project Operations Hub가 지금은 **규칙과 지식을 잘 정리하는 곳**이고, TeamAI는 그걸 **각 AI 환경으로 실제 배포하는 역할**을 맡을 가능성이 있습니다.

정리하면:
`Project Operations Hub = 원본 관리`
`TeamAI = 여러 AI에게 뿌려주는 배포기`

**주의:** `.codex`, `.claude`, hooks 같은 설정을 자동으로 만질 수 있으므로 현재 Hub에 바로 설치하지 않고 빈 테스트 저장소에서 먼저 확인해야 합니다.

**판단:** `먼저 시험`

## Codex with ChatGPT
링크: https://github.com/XiaoDuoYa/codex-with-chatgpt

**한 줄 설명:** **ChatGPT는 생각하고, Codex는 실제 작업하게** 둘을 연결하는 도구입니다.

**쉽게 말하면:**
ChatGPT가 프로젝트를 읽고
`계획 세우기 → Codex에게 실행 요청 → Codex가 수정/테스트 → ChatGPT가 결과 검토`
를 반복하게 만드는 구조입니다.

ChatGPT 쪽은 파일을 직접 수정하지 않고 읽기 전용 연결로 필요한 코드, git diff, 테스트 결과만 봅니다. 실제 파일 수정과 명령 실행은 Codex가 담당합니다.

**우리한테 왜 쓸모 있나:**
Sol/ChatGPT의 긴 맥락·검토 능력과 Codex의 실제 실행 능력을 역할 분담할 수 있어서, 우리가 원하는 **“말로 완료했다고 하지 말고 실제 diff와 테스트로 확인”** 방식과 잘 맞습니다.

**주의:** OpenAI 공식 제품이 아니라 커뮤니티 프로젝트입니다. 로컬 작업공간을 Cloudflare 터널과 MCP로 연결하므로 보안 검증 후 시험해야 합니다.

**판단:** `먼저 시험`

## Mimikyu
링크: https://github.com/3x-haust/Mimikyu

**한 줄 설명:** Figma를 보고 웹페이지를 만든 뒤 **얼마나 똑같은지 자동으로 숫자까지 재서 수정하는 Skill**입니다.

**쉽게 말하면:**
AI에게 “이 Figma처럼 만들어”라고 하면 보통 얼추 비슷하게 만들고 끝낼 수 있습니다.
Mimikyu는 거기서 끝내지 않고
`Figma 원본 → 웹 구현 → 스크린샷 → 픽셀 비교 → 글자 위치/색/크기 비교 → 다시 수정`
을 반복합니다.

그래서 “버튼이 16px 왼쪽이다”, “색이 정확히 다르다”처럼 **눈대중이 아니라 실제 수치로 틀린 곳을 알려줍니다.**

**우리한테 어디에 좋나:**
웹 대시보드, 게임 UI, 앱 웹뷰처럼 디자인을 정확히 맞춰야 할 때 좋습니다.

**필요한 것:** Node, Python, Playwright, Figma 접근권한/MCP 또는 토큰.

**주의:** Figma 토큰 같은 비밀값을 GitHub에 올리지 않아야 합니다.

**판단:** `프로젝트용`

## Blender MCP
링크: https://github.com/emeryporter/blender-mcp

**한 줄 설명:** AI가 실제 Blender를 만질 수 있게 연결하는 다리입니다.

**쉽게 말하면:**

# 실제 도입할 때만 보는 규칙

1. 여기 있다고 설치된 건 아닙니다.
2. SNS 게시물의 “몇 % 빨라짐” 같은 숫자는 참고만 하고 우리 PC에서 다시 확인합니다.
3. `.codex`, `.claude`, hooks, MCP 설정을 자동으로 바꾸는 도구는 빈 테스트 프로젝트에서 먼저 시험합니다.
4. API key, OAuth token, 비밀번호는 GitHub 문서에 적지 않습니다.
5. 외부 AI나 터널로 프로젝트 데이터가 나가는 도구는 어떤 파일이 나가는지 먼저 확인합니다.
6. 실제로 설치해보고 `설치 성공 → 실제 작업 성공 → 제거/복구 가능`까지 확인한 뒤에만 ACTIVE/PROJECT로 올립니다.
