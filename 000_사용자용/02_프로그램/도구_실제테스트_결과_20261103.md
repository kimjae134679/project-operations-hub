## 로컬 유틸리티와 Replica: 실제 입출력

- **jq1.8.2:** 한글 JSON에서 조건에 맞는 두 항목을 골라 이름 목록·합계를 변환하고 예상값과 일치함을 확인했습니다.
- **Ruff0.17.3:** 잘못된 Python의 F401을 실제 검출한 뒤 별도 수정 fixture에서 진단0을 확인했습니다. 설치파일이나 사용자 코드를 자동 수정하지 않았습니다.
- **PSScriptAnalyzer1.25.0:** Write-Host 경고를 검출하고 수정 fixture의 경고0을 확인했습니다. 지정규칙뿐 아니라 기본 전체규칙으로도 같은 bad/fixed결과를 확인했으며, 사용자 프로젝트 전체검사라는 뜻은 아닙니다.
- **Replica6개 helper의18개 기능검사:** 색 대비, 가중 parity/실패임계값, 자체 생성 PNG비교/실제diff파일, 합성 리뷰의 중복·링크없는행 처리/Markdown출력, 자체폴더의 이름·도메인잔재 탐지, listing길이·빈입력 검사를 실행했습니다. 도움말6회를 합쳐18이라고 센 것이 아닙니다. 예상된 진단/임계값의 nonzero는 검출성공이며 숨긴실패가 아닙니다. 설치helper의 hash는 전후 동일했습니다.

리뷰 입력과 PNG는 모두 소유한 합성자료입니다. 실제 서비스 리뷰 조사·앱 복제·화면캡처·게시·배포·실결제 검증이 아닙니다. 이전 Codex Skill12개 enabled인식 기록과 모델 workflow는 별도입니다.

## Apify: 등록된 문서 MCP 실제 조회

비공개config 전체나 토큰을 출력하지 않고, **등록된 apify-docs의 실제 command/args/env**로 stdio초기화·tools/list·공식 문서 조회를 실행했습니다. 도구는 search-apify-docs/fetch-apify-docs 두 개이며 Actor도구0, telemetryoff·격리HOME/토큰clear를 유지했습니다.

공식 `https://docs.apify.com/actors/running` Markdown **6,456자**를 가져와 문서 frontmatter/내용까지 확인했습니다. 허용된 공식 canonical URL에 한 번 GET했고 Actor·데이터셋·유료수집은 호출하지 않았습니다. 응답UTF-8 SHA256은 `3eaf92e8c2eccb457438b69008a5e2b9fd4ce5903851e3eddb196c09101e738d`이며 Windows CRLF로 저장된 파일hash와는 별도로 기록했습니다.

## 기본 도구와 Playwright 초기 실패·복구

Git의 임시 저장소 stage/diff·한글 경로, rg의 한글 정확검색, fd의 파일탐색, uv의 offline가상환경 생성/실제Python계산, Gitleaks의 가짜 공개토큰 검출·redact를 확인했습니다. 실제 사용자 비밀자료를 스캔하거나 commit/push하지 않았습니다.

Playwright1.63.0은 기본 Chromium1243을 요구했지만 기존 cache는1234여서 **초기 기본경로 확인이 실패**했습니다. 기존1234를 명시한 자체 HTML 한글 fill/click/DOM검사는 먼저 통과했지만 이것으로 기본조합을 정상이라고 하지 않았습니다.

이후 기존1.63 라이브러리의 **공식 Chromium1243와 headless1243만 추가 설치**했습니다. Windows 공식기본 cache를 유지했고 process-only PLAYWRIGHT_SKIP_BROWSER_GC=1로 기존자료를 보호했습니다. 기본 launch에서 executable/channel override 없이 한글 입력→버튼→DOM결과가 일치했고 **Chromium sandbox=true, network요청0**입니다. 기존cache611파일은 모두 hash동일,1234도 남겼습니다. 최초 불일치와 explicit1234결과 원본은 덮지 않았습니다.

이는 자체 in-memory HTML의 기능검증입니다. 사용자 브라우저·외부사이트·시각레이아웃·T3/OpenMaus앱 검증은 아닙니다.

## agent-desktop: 기능과 포커스 위험을 분리

명시 허가된 **자체 소유 격리 WinForms창**만 대상으로, strict-headless에서 한글 set-value → 의미적 button invoke → 새 snapshot·get으로 앱이 만든 결과를 재조회했습니다. 물리 마우스·키보드·클립보드·스크린샷·focus/activation명령은 쓰지 않았습니다. invoke가 delivered_unverified였으므로 재시도하지 않고 새 앱상태를 읽어 기능 성공을 확인했습니다.

하지만 처음 is_focused=false였던 자체창이 조작 후 true가 됐습니다. **“headless라 사용자 전경을 절대 방해하지 않는다”는 기대는 이번 테스트에서 실패**했습니다. set-value/invoke/Windows provider/framework 중 어느 것이 원인인지 단정할 근거가 없습니다. 발견 뒤에는 결과읽기와 해당창의 정상정리만 했고, 다른 전경앱을 조사하거나 포커스를 강제로 복구하지 않았습니다.

**권장:** 전경 보존이 필수이거나 사용자가 다른 일을 하는 동안에는 이 도구를 무간섭 자동화라고 가정하지 말고 파일/API/구조화된 연결을 우선합니다. 실제 UI조작은 명시 허가와 제한된대상·중단조건 아래에서만 사용하고 focus 변화가 생기면 멈춰 확인합니다. vendor/설치Skill을 임의 수정하거나 강제 포커스 복구로 감추지 않습니다.

## Codex: 응답은 왔지만 파일 과제는 실패

기존 ChatGPT요금제 경로에서 read-only·ephemeral·권한상승금지로 실제 요청1회/turn완료/exit0·응답을 확인했습니다. 요청한 모델은 gpt-6.1-sol이며 independent actualmodelID가 반환됐다는 증거는 없습니다.

그러나 소유한 한글 JSON을 읽으려는 Get-Content가 **실행 전에 policy거부**되어 기대 합계51을 구하지 못했습니다. 응답의 sum0은 성공한 계산결과가 아니라 읽지 못했다는 실패상태이며, exit0를 기능 PASS로 바꾸지 않습니다. 입력fixture2파일 hash는 변하지 않았습니다. 정확한 정책규칙은 미제공이고 대체 실행/추가 모델 재시도/선택적Replica모델테스트를 진행하지 않았습니다. 사용량은 기존 요금제 한도를 소모했으며 새 API과금 경로/키는 추가하지 않았습니다. 원문 모델trace는 공개repo에 넣지 않습니다.
